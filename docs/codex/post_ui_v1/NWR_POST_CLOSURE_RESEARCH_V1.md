## 2. Area-by-area evaluation (A-L)

### A. Player intelligence
Real current gap, precisely bounded. NWR has zero live real-time news/injury feed in production. It has exactly two free, admissible, already-built-but-inert shadow sources: nflverse's official weekly injury report (covers 9.2% of the canonical pool — expected, since only actually-injured players appear — but with a genuine `practice_status` signal NWR's manual overrides don't track) and Sleeper's public player catalog (85.3% identity-matchable via the existing `_identity` matcher, includes real IR/PUP/**Suspended**/Questionable status). A documented precedence design (manual override > nflverse/Sleeper shadow > no signal) already exists but is explicitly "a future, separate, deliberate decision — not performed by this pass."

Competitor reality check: Sleeper's own app pushes real-time injury/status alerts and a live news feed natively (confirmed via 2026 app-store/review research); FantasyPros' My Playbook surfaces player news across all synced leagues. NWR has nothing comparable in production. The gap is real, but the fix is narrower than "build a live feed" — it's "promote two already-free, already-matched, already-tested shadow sources into the existing `PlayerAvailabilityStatus` authority per the design that's already written." RotoWire/SportsDataIO/Sportradar remain the only paths to something closer to Sleeper's real-time push experience, and all three are `NEEDS_OWNER_CONTRACT` (no self-serve free tier).

### B. Multi-league usefulness
The Attention Center is read-only, manual-refresh, and deliberately cheap (never invokes the heavy Start/Sit/Waiver/Trade Finder/K-DST engines). It aggregates data-health/sync degradation, live-draft-in-progress, unresolved roster identity, a coarse waiver-opportunity flag, and playoff-deadline proximity, plus a genuinely useful cross-league player-ownership search. Competitor comparison: FantasyPros' Multi-League Assistant and Footballguys' MyFBG both do real per-league custom advice across synced leagues, but for a single owner with one real Sleeper league (Fantasy Gamers) plus a handful of local test/ESPN profiles, NWR's existing scope is not obviously missing anything a competitor does that would matter here — the gap would only become real if the owner joins several more *active, competitive* leagues at once. **No urgent gap identified.**

### C. Trade package quality
Real, live, tested: 1-for-1 through 2-for-2 packages (`MAX_PACKAGE_SIZE=2`, 900-package cap), Pareto-dominance filtering, three search modes, real per-side before/after roster-impact math, and a hard, tested "no acceptance probability, ever" rule. Competitor comparison: Sleeper's Trade Center is genuinely best-in-class for in-app negotiation (build/counter/manage offers with the real opponent) — but NWR deliberately never writes to any platform, so it structurally cannot and should not replicate that (a correct product boundary, not a gap). FantasyPros/Draft Sharks/RotoWire trade analyzers mostly reduce a trade to a single fairness score or grade; NWR's multi-dimensional breakdown (ROS value delta, starter holes, position redundancy, risk flags) is arguably *more* honest given the project's own anti-fabrication rule, not behind. The one real, disclosed gap — weekly-lineup ("this week") impact isn't wired into Trade Package Search's math — is a deliberate scope boundary, not an oversight. **3+-player expansion is NO LONGER WORTH IT**: real trades this deep are rare, and evaluation cost grows combinatorially for low incremental value.

### D. Matchup/playoff context
Real Sleeper-sourced week/matchup/standings/playoff-bracket data, wired as plain facts (record, points for/against, "Playoffs start Week 15"), with **no simulated finish or playoff-odds column** — an explicit, correct scope boundary matching the directive's "no premature championship simulator" rule. No real gap identified relative to what a personal app should responsibly show without fabricating probabilities.

### E. Prospective recommendation accountability
Real gap, cleanly bounded: `record_owner_action`/`record_outcome` are real, tested, callable backend functions with zero UI wiring. The History page literally renders "Not recorded"/"No outcome recorded yet" for every single row today. This is the most complete "backend built, feature not actually deliverable to the owner" item in the whole shift, and closing it does not require touching any hard-boundary scoring/legality file.

### F. Alerts/attention
Confirmed: nothing exists beyond the Attention Center's manual-refresh view — no polling, no push, no notification API usage anywhere in the frontend. Given (1) the underlying shadow-source coverage is partial (9.2%/85.3%, not universal), (2) Sleeper's own API guidance requires ≤1 fetch/24h caching for the player catalog, and (3) this is a single-owner desktop app the owner opens deliberately rather than a mobile app expected to interrupt them — proactive push-style alerting would be premature engineering investment relative to its real payoff today. **Manual refresh is the right call for now.**

### G. FAAB/manager descriptive intelligence
The directive's framing ("not built yet") is **out of date** — `suggest_faab_bids` is real, live, and wired: a contextual bid-range (not a fixed table) computed from real percentile standing in the live free-agent pool, a starter-upgrade multiplier, and a season-lateness taper, with an explicit, tested refusal to fabricate any competition/acceptance-probability signal. However, this pass found it is **currently broken in the UI**: the backend's real urgency values (`STARTER_UPGRADE`/`BENCH_DEPTH`/`LOW_VALUE`) don't match the frontend/contract's expected (`HIGH`/`MEDIUM`/`LOW`), so every FAAB urgency badge across Waivers/Improve Team/Weekly Home falls through to a generic "review" tone and displays the raw backend string, and the FAAB tab's urgency-based sort silently does nothing (every row ties at the same fallback rank). Beyond fixing this bug, "manager descriptive intelligence" in the sense of modeling *other managers'* bidding behavior would require a real competitive signal NWR doesn't have — building it would violate the project's own "no fake hidden-FAAB-bid predictions" rule. **Verdict: fix the real bug; do not build opponent-bidding modeling.**

### H. K/DST quality
Confirmed unambiguously across five separate files (`cheat-sheet.tsx`, `pages.tsx`, `fantasypros_kdst_consensus_service.py`, `udk_unmodeled_skill_asset_service.py`, `current_kdst_eligibility_service.py`): K/DST is pure FantasyPros ECR passthrough plus live Sleeper roster-ownership matching, with a formal taxonomy label (`EXTERNAL_UNMODELED_BY_NWR`) and repeated explicit UI copy ("NWR does not calculate a K/DST score"). One stale internal comment (`waiver_engine_service.py`) incorrectly claims a "real nflreadpy-backed matchup signal" for the streamer that does not actually exist in the implementation — worth a one-line doc correction. Competitor comparison: RotoBaller/FTN and other streamer-specific content incorporate schedule/opponent-points-allowed context that NWR's streamer currently doesn't show at all (schedule strength is explicitly named as available "in the DST/K streamer lane" in a comment that turns out to be aspirational, not real). Adding a schedule-context *annotation* (not a blended score — nflverse schedule data is already trusted elsewhere in this app) alongside the existing ECR table is technically feasible without violating the no-invented-NWR-model-score policy, but deciding to add ANY K/DST-adjacent signal is a real product-scope decision the app has so far deliberately avoided. **A taste/scope call, not a pure engineering fix.**

### I. Draft Room remainder
Draft Room V2 (`/draft-room-v2`) is confirmed an isolated candidate route, explicitly not replacing the production Draft Room at `/`. Cheat Sheet is genuinely shared/migrated (V2 imports the real `CheatSheetPage` component directly). The Player Drawer is explicitly, deliberately left un-unified in Draft Room ("DELIBERATELY left untouched"), and several controls (pick correction, ADP refresh, recent-picks log) are annotated as "ported from Legacy verbatim," meaning the older Draft Room remains the real source of truth underneath. Given the owner drafts once per season and the legacy room has been repeatedly re-verified as fully functional across this entire shift with zero hard-boundary drift, **visual consistency here is cosmetic, not a functional gap** — genuinely low value relative to the weekly-use surfaces this shift actually improved.

### J. Performance
Confirmed via the real, instrumented release-gate smoke script: Waivers (Improve Team, THIS_WEEK mode) measured at **16,318.1 ms**, and the Weekly Home actions aggregation at 7,936.2 ms — both dramatically slower than every other traced surface (most surfaces are sub-2s; even the Sleeper import itself is ~2.4s). No pass has investigated the root cause; it's flagged every time as "out of scope for a verification-only pass." Given these are surfaces a real owner would open every week (Weekly Home is the literal front page; Waivers/THIS_WEEK is the natural weekly-planning view), an 8-16 second wait each time is a genuine, user-visible UX cost — well past the point where a personal desktop app should feel instant. **Worth a real profiling pass** (likely candidate root causes visible from the code: `redraft_weekly_home_actions` internally re-invokes `redraft_weekly_lineup`/`redraft_waivers`/`redraft_trade_finder`/`redraft_kdst_streamer` as separate live-Sleeper-backed sub-calls rather than sharing one fetch, and THIS_WEEK waiver mode likely does an live per-candidate weekly-projection resolution across the whole free-agent pool).

### K. Release reliability
Real, substantial progress since the directive's framing: `check:resources` (the packaging privacy gate) is now genuinely fixed via a real two-artifact governance-receipt architecture, and a real native build succeeded once (NSIS `.exe` + MSI, "Finished 2 bundles," a privacy scan of the extracted payload found zero real owner-identity leaks). What's still missing before this is "genuinely shippable to the owner's own machine day-to-day": (1) **no actual install-and-launch was ever performed** — every pass explicitly disclosed this as "a static content/privacy scan of the extracted payload, not an actual install + first-run launch"; (2) no code signing/auto-update mechanism exists at all, meaning a real install will trigger a Windows SmartScreen warning the owner has to click through — a real, if minor, first-run friction point for a personal app; (3) the installer currently on disk (if any survives between worktrees) reflects a build one commit behind the final decision-trace dedup fix — harmless but stale; (4) a low-severity, disclosed build-machine-path leak (the build account's Windows username, not the owner's) sits in Rust panic-string debug info, fixable via a compiler flag. None of these are vendor-gated; the install-and-launch gap in particular is real, cheap to close, and the single most concrete remaining item before calling packaging "done."

### L. Owner workflow friction
Having read the actual code across every surface, the two most concrete, currently-live friction points for a real owner clicking through this app day-to-day are: (1) the Waivers/Weekly Home latency from Area J — an 8-16 second wait on the two most-visited weekly surfaces is the kind of thing a human notices and complains about, unlike most of this shift's other disclosed gaps, which are either invisible (schema-only tool types) or genuinely rare (once-a-season draft visuals); (2) the FAAB urgency bug from Area G — a badge that literally renders "STARTER_UPGRADE urgency" as its label, with the wrong color every time, is a small but real "this looks broken" moment that undermines trust in an otherwise carefully-disclosed, honest app. Both are small enough to fix without touching any hard-boundary file.
