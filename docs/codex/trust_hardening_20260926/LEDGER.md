## Market Staleness Investigation (the exact, targeted item the dispatch asked for)

**Exact source found**: `src/services/trade_roster_negotiation_service.py`, module-level constants at lines 25-26:
```python
MARKET_LABEL = "Market negotiation context — stale as of 2026-07-17"
MARKET_DATE = "2026-07-17"
```

**What this code path actually does** (INSPECTED, full file read): `build_market_negotiation_context()` (line 542) computes a same-snapshot display total of external DynastyProcess (`market_dp_value`) figures for a proposed trade's "give"/"receive" sides. Its `_market_side()` helper (line 912) only includes a row's DP value if that row's `market_status` field contains a date string that **exactly, literally matches** the hardcoded `MARKET_DATE = "2026-07-17"` constant (`_market_date()` extracts a `\d{4}-\d{2}-\d{2}` pattern via regex and compares it for exact equality — not "is recent enough," but "is this exact date"). This means the constant is not merely a label describing observed staleness — it is a **hard, literal admission gate**: even if the underlying admitted data pack were refreshed to a newer date tomorrow, this function would silently exclude every row from that newer snapshot (treating them as `excluded_assets`, same as a genuinely missing value) until a human edits this source file to bump the constant. It is a real, functioning feature (never mixes two different snapshot dates into one displayed total — `same_snapshot` check at line 557), but its mechanism for staying current is "someone edits a Python constant," not "reads the freshness report."

**Why the date is stale**: this constant reflects whatever admitted DynastyProcess data-pack snapshot was current at the time this file was last touched (2026-07-17), and — critically — **the underlying refresh mechanism the app actually uses today for market data has moved on without this file being updated to match**. `src/services/market_baseline_service.py` and `src/connectors/dynastyprocess_connector.py` implement a real, live, still-functional DynastyProcess fetch pipeline (public GitHub raw CSVs, schema-validated, with a genuine 6-state freshness vocabulary — see `DATA_SOURCE_LEDGER.md` §3) that has no dependency on this hardcoded date at all. That pipeline reports its own real freshness (`"Stale as of {date}"` / `"Current as of {date}"`, computed dynamically from the CSV's own `scrape_date` column) via a completely different code path: `owner_asset_evidence_service.py`'s `_market_status()` (line 182), which is what the LIVE desktop Dynasty Trade Decision Lab actually consumes.

**Is the stale-labeled code path even reachable from the live app?** **No — confirmed dead from the live desktop app's perspective.** `grep -rn "trade_roster_negotiation_service"` across `src/`, `app/`, and `desktop/` shows exactly one importer in the entire repository: `app/pages/23_trading_lab_v1.py`, the legacy Streamlit "Trading Lab v1" page that predates the live Redraft/Dynasty desktop product entirely (the same demoted `app/` sub-product `PRODUCT_ARCHITECTURE.md` already documents as legacy). `src/application/desktop_facade.py` never imports `trade_roster_negotiation_service` anywhere. The live desktop Dynasty Trade Decision Lab (`evaluate_dynasty_trade` in `desktop_facade.py:1527-1584`, backing `/api/v1/dynasty/trades/evaluate`) calls a completely separate module, `trade_decision_assistant_service.py`, which sources its market context through `owner_asset_evidence_service.py` → `market_baseline_service.py` — the real, dynamically-freshness-labeled pipeline, not this hardcoded constant.

**Precise summary for the next worker (Worker 2)**: the literal string the owner's directive quotes is real, findable, and precisely explainable — but it originates from a legacy Streamlit page that a prior cycle already determined is not part of the live product, not from the live desktop app's actual trade-evaluation surface.
